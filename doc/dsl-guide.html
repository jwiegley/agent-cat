agent-cat · the workflow language · a guide

Writing Workflows That Can Be Read, Priced, and Run

A small language for putting questions to models, tools, and people — and for saying, before anything runs, what a program will ask and what it may cost.

A program in this language names the questions a workflow puts and the order in which their answers flow into one another. It is text, it is checked before it runs, and the checked result is the same mathematical object the library proves theorems about. Three commands act on a program: one prints what it says, one prices it, and one runs it against an agent.

One A first program, line by line

Here is the whole of example/hello.wf: two questions and an act.

-- The smallest program that is still a workflow.
define brief = "Reply in one short line."

workflow {
  let subject = ask tool "cat" for text
    "Name one thing worth greeting.\n{brief}"

  let greeting = ask model "greeter" for text
    "Write a greeting for this, and nothing else:\n{subject}\n{brief}"

  act tool "say"
    "Say it:\n{greeting}\nThen reply DONE."
}

Read it as five decisions. define introduces a piece of text used more than once; the parser expands it, so nothing of it survives into the program. workflow { … } encloses the body, which is a sequence of bindings ending in an act — or simply running out, since a list of things to do that runs out is over. Each let puts one question and binds its answer to a name. ask tool "cat" says who is asked; for text says the answer wanted is free text. Inside a prompt, {subject} splices an answer already in scope, which is how one question's reply becomes part of the next question's words.

Three rules hold everywhere in the language, and the rest of it is their consequences. A scope is a pair of braces — every region in which a name is visible is { … }, and indentation means nothing anywhere. A name is introduced by a word that says a name is being introduced — define x = and let x = for a name bound to an answer, given x for a name a clause is handed, and there is no third way. A prompt is the last thing in its phrase, and the kind sits between the addressee's name and the words, so no two string literals are ever adjacent in an ask and nobody has to know an arity to see where a phrase ends.

Two more points are worth grasping early. A name is bound to an answer, not to a question, so mentioning {brief} twice costs nothing and mentioning {subject} twice puts no second question: sharing is binding. And an act is terminal: act puts a question whose answer carries no information, and nothing follows it in the block.

Two The vocabulary

The language has eight constructs and thirty-eight lexemes. Each construct names an object the library already has, and the checker translates it into that object rather than into an interpretation of its own.

Asking

ask <addressee> for <kind> "words"
ask <addressee> draw <n> for <kind> "words"
ask <addressee> using model "name" for <kind> "words"

Four kinds of answer exist, and the kind is part of the question rather than a hope about the reply.

KindThe answer isUsed for
textfree textdrafts, summaries, guides, anything read by a later prompt
verdictapproval, objections, or a refusalreviews; the only kind a panel may combine
flagyes or noconsent, gates, two-way branching
acknothingacts, where the point is the effect and not the reply

Three addressees exist — model "name", tool "name", and person "name" — and they are recorded in the question, not in the runtime. A person is an addressee like any other; asking one for consent is an ordinary question whose answer is a flag.

draw n marks an independent resample. Two questions with identical words and different draws are two questions and are answered separately; without it they are the same question and are answered once. using model "name" directs one question to a particular model, and it rewrites that question's own scope rather than wrapping anything, so it never leaks onto the questions that follow. Read the two together as English: ask model "author" says who is asked, using model "deep" says which model serves it, and the two prepositions keep two different fields of the question apart.

Binding

let name = <ask or panel>

Puts the question, binds the answer, and continues. The name is in scope for every prompt after it, and only for prompts after it.

Panels

panel [ <ask>, <ask>, … ]

Several reviewers answer, and their verdicts combine into one: approval is the unit and any objection carries, so a panel approves exactly when every member approves and otherwise reports the objections raised. Only verdict may be panelled, because combining answers requires a way of combining them and that is the only kind that carries one. The members are ordinary asks, so each may have its own addressee, its own model, and its own words.

Bounded revision

revising <subject> up to <n> revisions {
  check  given a       { <ask or panel yielding a verdict> }
  revise given a, why  { <ask yielding the artefact's kind> }
}
approved given a { <block> }
never approved   { <block> }

The loop's braces hold exactly the loop. check reviews the current artefact; if it objects and revisions remain, revise produces a new one — why is bound to the objections as text — and the cycle repeats. Each clause says given because each is handed its names: the author does not choose the artefact, the loop hands it over, and a in check, in revise and in approved are three different binders that happen to share a spelling.

The two clauses after the braces are the two ways the loop can end, and they are outside because they are not part of it: approved given a runs with an approved artefact in hand, never approved runs when the budget ran out with objections outstanding, and there is no artefact to hand it. Each outcome is the rest of the workflow — control does not rejoin, and nothing follows them — which is why they are written as two clauses of one statement rather than as a value some later line consumes.

Note the order and count: up to n revisions performs n + 1 checks and at most n revisions. The unit is named where the numeral is precisely because three independent readers of the library got that number backwards. Both spellings are accepted, so up to 1 revision is English; it is the only word in the language with two spellings. The artefact reaching approved has always been reviewed, which is the property worth having and the one easily written backwards.

Branching

if flagName { … } else { … }
case verdictName { approve { … }  object { … }  declined { … } }

Every arm is written out; there is no default, no fall-through, and no elidable else. This is not strictness for its own sake. An arm that is present in the program can be priced whether or not any run takes it, which is what allows a branching program to have a cost analysis at all — the flagship's nine-leaf cost tree counts the arm nobody takes, and an author who cannot see that arm cannot read the bill.

A branching is a tail: each arm is the rest of the workflow, and nothing follows the branching in its block.

Ending

act <addressee> "words"     -- do the thing; nothing follows
{ }                         -- a block that does nothing; there is no word for it

A block is a list of things to do, and a list that runs out is over: { } does nothing, and { let x = ask … } asks and stops. Doing nothing therefore looks like doing nothing, which is what the language has instead of a keyword for it.

Prompts

A prompt is a string in which {name} splices a bound answer. The escapes are \n, \t, \r, \\, \", \{, and \}. Only text-valued names may be spliced, with one exception the language grants rather than waives: inside revise given a, why, the objection binder why is bound to the verdict already rendered as text, so the renderer is written where the binder is.

Three What the checker will not allow

Checking is not validation followed by a hopeful cast. The checker constructs a well-typed plan as it reads, so a program that is accepted is a plan; there is no intermediate state in which an accepted program is ill-typed. Refusals name the construct and the position. The messages below are the ones the tools print.

RejectedThe message
a name that is not in scopeunbound name; nothing in scope answers to it
splicing a non-text answeronly a text answer interpolates into a prompt, but `review` answers `verdict`
a clause given the wrong kindexpected an answer of kind `verdict`, …
a panel of anything but verdictsa panel combines its members' answers in the monoid of their kind, and only `verdict` carries one
a revision bound above 64a bounded revision is unrolled into the term it writes, so its bound may name at most 64 revisions
a question in tail positiona question here has nowhere to put its answer: write `let x = ask …`, or `act` if the point is the doing
let p = revising …a bounded revision has two outcomes and is not an answer to bind: write its `approved given …` and `never approved` clauses after its braces
a statement after a tailexpected `}`: `act`, `if`, `case` and `revising` are tails, and a tail ends its block
an outcome clause missingexpected `approved given <name> { … }`: a bounded revision writes both of its outcomes
if on something elsean `if` branches on a flag, but `x` answers `text`
using model after the kind`using model` says which model serves the addressee, so it is written beside the addressee and before `for`
a name mentioned where no clause was handed itunbound name; nothing in scope answers to it — this is what mentioning the artefact inside never approved gets, and it is the truth: there is no artefact there

Two of these deserve their reasons. The bound of sixty-four is not a matter of taste: a bounded revision is unrolled into the term it writes, so a bound of a billion is a billion-node term, and elaborating it exhausts the stack before anything runs. Every accepted program is bounded, and that is a proved property of the language rather than a guard on one clause. The panel restriction is the same principle from the other side: combining answers needs an operation with a unit and an associative combination, verdicts have one, and free text does not.

Four A full workflow, annotated

This is example/harden.wf, the program the library's theorems are about. Draft a patch under a designated model; review it with three reviewers, two of whom read a shared style guide; revise up to twice; ask a person; apply only on assent.

define spec        = "harden the parser"
define verdictSpec = "Reply with exactly APPROVE if acceptable, or OBJECTION: <one line> if not."
define flagSpec    = "Reply with exactly yes or no."

workflow {
  -- Asked once. Both reviewers below splice this one answer.
  let guide = ask tool "cat" for text
    "Write out the house style guide, at most four short lines."

  -- `using model` directs this question, and only this one, to the deep model.
  let draft = ask model "author" using model "deep" for text
    "Draft a patch satisfying:\n{spec}\nReply with a unified diff only."

  revising draft up to 2 revisions {
    -- Three verdicts, combined: any objection carries.
    check given patch {
      panel [
        ask model "reviewer-correct" for verdict
          "{guide}\nIs this patch correct?\n{patch}\n{verdictSpec}",
        ask model "reviewer-secure" for verdict
          "{guide}\nIs this patch secure?\n{patch}\n{verdictSpec}",
        ask model "reviewer-simple" for verdict
          "Could this patch be simpler?\n{patch}\n{verdictSpec}"
      ]
    }

    -- why is the objections, as text.
    revise given patch, why {
      ask model "author" using model "deep" for text
        "{guide}\nRevise this patch:\n{patch}\n{why}\nReply with the revised diff only."
    }
  }

  -- Reached only with a reviewed patch in hand.
  approved given patch {
    let ok = ask person "owner" for flag
      "Apply this patch?\n{patch}\n{flagSpec}"

    if ok {
      act tool "apply"
        "Apply:\n{patch}\nWrite the patched file here, then reply DONE."
    } else { }
  }

  never approved { }
}

Read aloud with no glossary: let guide be what you get when you ask the tool cat for text, saying this; let draft be what you get when you ask the model author, using the model deep, for text. Revising draft, up to two revisions: to check it, given a patch, put this panel of three questions; to revise it, given a patch and why it was rejected, ask the author again. Approved, given the patch: let ok be what you get when you ask the person owner for a flag; if ok, act through the tool apply; else do nothing. Never approved: do nothing.

Everything the workflow guarantees is visible in the text. The guide is bound once, so it is asked once however many reviewers read it. The act sits inside the if arm of a branching on a person's answer, so no run can apply a patch nobody approved. The revision budget is written, so the number of drafts is bounded by the program rather than by hope. And patch is declared three times, once in each clause that is handed it, so there is no scope to explain and no name in never approved that seems to mean an artefact that does not exist.

Five Reading, pricing, running

All three commands share one front end: the same reader, the same checker, the same diagnostics, and exit status 2 on a program that does not check.

agent-cat plan example/harden.wf

Prints the checked term as the library holds it — not the source read back, but the object the source produced.

nodes: 36   consultations written: 19   level: branch

  askC    text    tool cat                model=- mode=-   draw=0  binds #0
    | Write out the house style guide, at most four short lines.
  askC    text    model author            model=deep       draw=0  binds #1
    | Draft a patch satisfying:
    | harden the parser
  ask     verdict model reviewer-correct  model=-          draw=0  binds #2
    | {#0}
    | Is this patch correct?
    | {#1}

Two spellings of a question appear. askC carries its words in the term, because nothing in them came from an earlier answer; ask computes its words from the answers in scope, and {#0} marks where the answer bound at distance zero is spliced. The rendering is useful precisely for checking that a prompt splices what its author intended.

agent-cat cost example/harden.wf

Prices the program without running it, and says what kind of statement each number is.

level: branch   consultations written in the term: 19   nodes: 36
shape sequence: NOT fixed by the term — this program branches, and the cost
  tree below is what stands in its place.
cost tree: 9 leaves, cheapest 5, dearest 15 consultations
attained: NOT computed, and not computable from the term alone… a `case` prices
  its arms independently while a world correlates them, so a leaf need not be
  the bill of any run. Read the cheapest above as a lower bound that may be
  unattained.
what holds of every world: its bill is one of the leaves…

On a program that does not branch, the report is sharper: the shape sequence is printed outright, because the term fixes every question that will be put. The distinction is the point of the level, and it is discussed next.

agent-cat run example/harden.wf

Runs the program against an adapter — --adapter stub by default, --adapter claude for a live agent — and prints the transcript, the turn latencies, both bills, and the certificate.

bill: 7 consultations fresh, 7 memoized
ok   every replayed event is recorded in the run's table
ok   table size = billMemo tick (one entry per distinct question)
ok   the bill (7) is one of the cost tree's leaves
ok   the run certifies

The last line is the one that connects a run to the mathematics: the answers actually given are replayed as a world, the program is evaluated in that world, and the result is compared with what the run produced.

Six What the language deliberately cannot say

A workflow may be classified by how much of its behaviour is fixed by its text. Three of the four possible levels are reachable in this language, and the fourth is not.

LevelReached byWhat can be said before running
batchquestions with no spliced answersthe exact question list, and the exact bill
pipelinesplicing answers into later promptsthe exact sequence of questions to be put, and the exact count
branchif, case, and hence revisinga finite tree of possible bills, with least and greatest
dynamicnot expressiblenothing: no finite set of bills exists

The library's plan type has a node for a plan computed from an unbounded answer, and the language has no syntax for it. The consequence is a proved property of every program anyone can write here: the level is at most branch, so a cost analysis always exists. That is the trade the language makes. A workflow whose shape must be chosen by a model — a planner that decides which sub-workflow to run — cannot be written in this text and must be written in Lean against the plan type directly. In exchange, every program that can be written can also be priced.

Seven Patterns and pitfalls

A review panel over a shared reading

Bind the shared material once and splice it into each member. The guide is consulted once no matter how many reviewers read it, and the transcript shows one consultation.

A human gate before an effect

Ask a person for a flag, branch on it with if, and put the act in the taken arm alone; the else arm is written as { }, because doing nothing is a thing the program says rather than omits. Two properties follow from the text: no run applies without assent, and a refusal costs one consultation less than an assent, which is visible in the bill.

Best of several drafts

Give each attempt its own draw, then judge them. Without distinct draws the attempts are the same question and receive the same answer; with them they are independent, and the resampling is written down rather than assumed.

let a = ask model "author" draw 0 for text "Draft a patch for:\n{spec}"
let b = ask model "author" draw 1 for text "Draft a patch for:\n{spec}"
let pick = ask model "judge" for verdict "Which is better?\nA:\n{a}\nB:\n{b}\n{verdictSpec}"

Revision that always reviews what it returns

Use revising rather than a hand-built loop of asks. Its clause order is check-then-revise, so the artefact reaching approved given … has been reviewed; a loop written by hand tends to revise last and hand back something nobody looked at.

Pitfalls worth naming

  • Two prompts with identical words are one question. That is usually the intent and occasionally a surprise. Distinguish them with draw, or with different words.
  • A cheapest bill is not a price. The cost tree prices arms independently while a run correlates them, so its minimum may be paid by no run at all. The report says so; do not quote the number without the qualification.
  • Kinds are contracts with the addressee. Asking for a flag obliges the prompt to say how to answer one; the runtime's decoders are deliberately strict, and a reply that cannot be read aborts the run rather than being guessed at.
  • using model attaches to one question. To direct several, write it on each; there is no block-level form, and this is deliberate, since a scope that leaks is a scope nobody can read off the text.
  • A tail ends its block. Nothing may follow act, if, case or revising: each arm and each outcome is the rest of the workflow. If two arms need the same sequel, write it in both — the language will not pretend control rejoins where the mathematics says it does not.
  • Three clauses, three binders. check given patch, revise given patch, why and approved given patch each introduce their own patch. Spelling them alike is a convenience for the reader; they are three different names, and none of them is in scope in never approved, where there is no artefact.

Eight Reference card

program  ::= {define} "workflow" block
define   ::= "define" name "=" string

block    ::= "{" {binding} [tail] "}"
binding  ::= "let" name "=" rhs
tail     ::= act | if | case | revising

rhs      ::= ask | panel
ask      ::= "ask" target ["using" "model" string] "for" kind string
panel    ::= "panel" "[" ask {"," ask} "]"
act      ::= "act" target string

target   ::= ("model" | "tool" | "person") string ["draw" nat]
kind     ::= "text" | "verdict" | "flag" | "ack"

if       ::= "if" name block "else" block
case     ::= "case" name "{" "approve" block "object" block "declined" block "}"

revising ::= "revising" name "up" "to" nat ("revision"|"revisions") "{"
               "check"  "given" name          "{" rhs "}"
               "revise" "given" name "," name "{" rhs "}"
             "}"
             "approved" "given" name block
             "never" "approved" block

string   ::= "…"  with {name} interpolation and \n \t \r \\ \" \{ \} escapes
punct    ::= { } [ ] , =
comment  ::= -- to end of line

There are no reserved words: a word is a keyword only where that word is expected, so the lexer stays a function of characters alone. Removed from the previous surface: upto, done, exhausted, accepted, with, yes, no, and the four punctuation marks @, ->, (, ). Added: for, using, up, to, revision(s), given, revise, approved, never, if, else. Five more words, four fewer punctuation marks, and nothing taken out of the language.

Limit or ruleValue
revision boundat most 64; up to n revisions is n + 1 checks and at most n revisions
panelsverdict only
interpolationtext-valued names, and why inside revise given …
program resultnothing; a block ends in a tail or simply runs out
