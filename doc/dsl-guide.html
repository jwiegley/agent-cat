agent-cat · the workflow language · a guide

Writing Workflows That Can Be Read, Priced, and Run

A small language for putting questions to models, tools, and people — and for saying, before anything runs, what a program will ask and what it may cost.

A program in this language names the questions a workflow puts and the order in which their answers flow into one another. It is text, it is checked before it runs, and the checked result is the same mathematical object the library proves theorems about. Three commands act on a program: one prints what it says, one prices it, and one runs it against an agent. This guide describes the surface approved in round ten of the redesign; the design record, with the grammar of record and its history, is doc/research/dsl-redesign/.

OneThe whole language on one page

This is example/harden.wf, the flagship: draft a patch, have three reviewers pass on it, amend it at most twice, ask the owner, and apply it only if they consent.

define spec        = "harden the parser"
define verdictSpec = "Reply with exactly APPROVE if acceptable, or OBJECTION: <one line> if not."
define flagSpec    = "Reply with exactly yes or no."

workflow {

  guide <- ask tool "cat"
      "Write out the house style guide, at most four short lines."

  draft <- ask model "author" served by "deep" ```
      Draft a patch satisfying:
      {spec}
      Reply with a unified diff only.
  ```

  result <- revising draft as patch, at most 2 amendments {

    verdict <- panel, all must approve [
      ask model "reviewer-correct" ```
          {guide}
          Is this patch correct?
          {patch}
          {verdictSpec}
      ```,
      ask model "reviewer-secure" ```
          {guide}
          Is this patch secure?
          {patch}
          {verdictSpec}
      ```,
      ask model "reviewer-simple" ```
          Could this patch be simpler?
          {patch}
          {verdictSpec}
      ```
    ]

    amend patch {
      ask model "author" served by "deep" ```
          {guide}
          Revise this patch:
          {patch}
          {verdict}
          Reply with the revised diff only.
      ```
    }
  }

  case result {

    settled patch {
      ok <- ask person "owner" ```
          Apply this patch?
          {patch}
          {flagSpec}
      ```

      if ok {
        ask tool "apply" ```
            Apply:
            {patch}
            Write the patched file here, then reply DONE.
        ```
      } else { stop }
    }

    unsettled { stop }
  }
}

Read the left edge: guide, draft, result, verdict, patch, ok — every name introduced by the same arrow, in the order it arrives. A value is consumed in exactly two ways — a {hole} in a prompt, or a branching — so who can see what is answered by searching the page: {guide} appears in four prompts, and the simplicity reviewer's absence from that list is visible in the same scan.

Braces delimit; indentation means nothing; comments run -- to the end of the line. There are no reserved words — positions decide — and doing nothing is written stop, never { }.

TwoBindings, and where kinds come from

A binding is name <- source. There is no let: the arrow says it. A name answers one of four kinds — text, verdict, flag, receipt — and the kind is usually inferred from the name's first ground use, in reading order:

usekind it fixes
{x} in a prompttext
if xflag
case x { approved … }verdict
bound from a panel, or the review binding of a loopverdict, by position
the subject of a revisingshares its carrier's kind

A later use that disagrees is refused by the ordinary kind-mismatch diagnosis — so the first use fixes the kind and nothing silently converts. An annotation is always legal (guide : text <-) and is required in exactly one situation: a bound name with no ground use at all, where the refusal names the annotation. One consequence to know: under inference, adding or removing a use of a name can change which question its binding asks.

Two more rules about names. A live name is never introduced twice — a name whose scope has ended may be reused, which is exactly what lets the settled arm call its artefact patch after the loop's carrier patch has died. And a binder may not spell a define: the two namespaces never merge.

You may also freeze the scope on the page: known here: patch, draft, guide is an assertion of exactly the names in scope, innermost first, and the checker refuses the program if it is wrong. It is documentation that cannot rot. known here: nothing asserts an empty scope.

ThreePrompts: strings, blocks, and the three holes

A prompt is a quoted string — with the escapes \n \t \r \\ \" \{ \} — or a text block: a fence of three or more backticks at the end of the line, the content on the following lines, closed by the first line whose first non-blank characters are exactly the same number of backticks. The block's non-blank lines are dedented by their longest common indentation, blank lines are kept (they are Markdown's paragraph breaks), and the lines are joined with newlines. What the addressee is told is exactly what the file shows, shifted left.

Inside a block, three things are special: a hole, and \{ / \} for literal braces. Everything else — quotes, backslashes, shorter backtick runs — is literal, so pasted Markdown survives verbatim except for {. Markdown containing a three-backtick fence is quoted with a four-backtick outer fence, which is CommonMark's own escalation rule. Mixed tabs and spaces in a block's indentation are refused rather than guessed at.

The three holes, in either spelling of a prompt:

holemeaning
{x}an answer, spliced as text when the program runs: a text answer is itself, a verdict is its objections joined by "; " (approval and no-answer splice as nothing); flags and receipts are refused — they have no canonical text
{d}, where d names a defineliteral text, expanded where you see it, before anything runs — the question stays closed

One spelling serves both because it cannot be ambiguous: a hole's name is a define or a binding, never both — a binder may not spell a define, and the checker refuses the collision — so the name alone decides. A question is closed, and priced at the batch rung, exactly when every hole it wrote named a define, which the preamble at the top of the file decides; agent-cat plan names each question's rung.

A define is one name for one piece of literal text, written once, before workflow. A define's body may hole only earlier defines, a duplicate define is refused, and agent-cat --define name="…" replaces a define's body at load time — same program, different words — and refuses a name the program never defined.

FourQuestions, addressees, and the act

x <- ask model "author" served by "deep" independent draw 2 "…"
x <- ask tool   "cat" "…"
x <- ask person "owner" "…"

Three addressee kinds, one shape. served by "m" names the model that serves a model addressee, and is refused on a tool or a person, where it would name nothing. independent draw n is a deliberate resample: asking the same question twice yields the same answer — sharing is the meaning, not a cache — so a fresh opinion is a different question, and the draw index is what makes it one. It is legal on all three addressees: a blind re-review by a person is as deliberate a resample as a fresh sample from a model.

An ask written in statement position, binding nothing, is the act: it asks for nothing back (its answer kind is receipt, which carries no information), and the workflow continues after it. The flagship's ask tool "apply" is one. Two honest limits: the absence of an arrow marks discard, not consequence — the run-time permission layer is what distinguishes an act (it may write) from every other question (denied writing) — and a receipt verifies nothing, so a prompt should not demand a completion token nothing checks.

FiveBranching, and the revision loop

A flag branches like any normal language: if ok { … } else { … }, both arms mandatory — both paths are priced, so both are written. A verdict branches with case, every arm written, in order:

case v { approved { … } objected { … } no answer { … } }

Branchings are tails: each arm is the rest of the workflow, and nothing follows a branching in its block. Arms export no bindings.

The loop:

result <- revising draft as patch, at most 2 amendments {
  verdict <- … one verdict-answering source: an ask, or a panel …
  amend patch { … one source producing the next patch … }
}
case result {
  settled patch { … }
  unsettled     { … }
}

Read it as its own sentence: revise draft, calling the moving candidate patch, at most 2 amendments. Each round binds one verdict — an ordinary binding with a name you choose, consumed by the normal scope rules ({verdict} in the amend prompt, where a verdict splices as its objections) — and the loop settles the moment a review approves; otherwise the amend block's answer becomes the next patch, its head naming what it replaces. at most n amendments is between one and n+1 reviews and at most n amendments, and the unit agrees with its numeral (at most 1 amendment).

The loop's result is settled-or-not — not one of the four kinds, so it is not an ordinary value: the very next statement must be its case, the settled arm names the artefact where it exists, and unsettled is the path the author must write for a loop that never came to rest. Nothing else may touch the result, and a result nothing consumes is refused.

SixPanels

verdict <- panel, all must approve [ ask …, ask …, ask … ]

Several questions asked side by side, their verdicts combined — and the rule is on the page. The menu currently has this one entry: all must approve is the verdict monoid — objections concatenate in member order, and one member who does not answer sinks the whole panel to no answer, deliberately: silence is not an opinion to outvote. A panel always answers verdict (no other kind carries the monoid), and a bare panel [ … ] is refused: a panel that does not say its rule leaves the reader to guess.

One hazard, named rather than hidden: under all must approve, a member who declines annihilates every other member's objections, so a revision's {verdict} can legitimately splice as empty text — the reviser is told it failed but not why. The designed second entry, at least n must approve, fixes this for n < k and is specified in doc/research/dsl-redesign/panel-rules.md (obr acat-f10).

SevenFunctions and libraries

A function is a reusable sequence of questions: typed parameters, one declared result, a straight-line body.

function judged (patch : text, rubric : text) -> verdict {
  v <- ask model "judge" ```
      Judge this patch against the rubric.
      {patch}
      {rubric}
  ```
  answer v
}

A call is written by juxtaposition and reads like the sentence it is: second <- judged patch "the rubric". An argument is a name or quoted words (words fill a text parameter); a call is not an argument — bind it first. Long arguments have two spellings: one trailing block fills the last parameter, and a $label in the argument list is answered by a labelled block written after the call:

second <- judged patch $rubric
```rubric
    A patch passes when it is minimal, tested, and reversible.
```

A body is bindings, acts and calls, ending with answer name — except a -> receipt body, which just ends and is called in statement position, like the act it is. A body cannot branch, cannot revise, and cannot see its caller's names (its parameters are its whole world, by type); a call head resolves against the functions declared above it, so recursion is unwritable. Parameters answer text or verdict: a flag parameter would smuggle a decision into a body that cannot branch, and a receipt carries nothing to pass. A call inlines — the function's plan is substituted at each site (Plan.sub: a call is the library's own substitution, not a new former) — so agent-cat plan prints exactly what runs, and two calls with the same arguments are one answer, as sharing always is.

A library is a file with no workflow block: defines, functions, and top-level statements — its priming, which runs at load, before anything the importer writes. import lib reads lib.wf beside the program (the CLI resolves; all modules of one program live in one directory), and everything a library exports is read qualified — lib.guide, lib.judged, {lib.spec} — so a library can never collide with your names: the shadowing problem is dissolved, not ruled on. A library's top-level bindings are annotated, always — inference scans forward, and forward is the importer's text. Imports run post-order, each file once, cycles refused by name; transitive imports execute but do not re-export. A program cannot be imported, and a library may be run: its priming, then nothing — agent-cat cost lib.wf prices the standing context. The elaborated term is priced before it is built: a function or a program whose inlining would exceed maxQuestions is refused with the count.

EightWhat the checker will not allow

Refusals name a position, say what is wrong in one sentence, and quote the fragment. The ones worth knowing before you meet them:

you wrotethe refusal
a bound name with no use and no annotationnothing fixes what kind of answer it names: use it, or annotate it
{ok} where ok is a flaga flag has no text of its own; only text and verdicts interpolate
a binder spelling a define, or a second define of one namethe namespaces never merge — which is what makes one hole spelling unambiguous
re-introducing a live nameno shadowing; rename one of the two
{ }a path that does nothing says so: write stop
a revising result nothing consumes, or touched by anything but its casethe case is the next statement, and nothing else touches it
served by on a tool or a persononly a model addressee is served by a model
case ok { yes … no … }a flag branches with if … else
at most n amendments above 64the loop is unrolled into the term, so the bound is a resource limit (maxRevisions)
a block mixing tabs and spaces, or a fence nothing closesrefused at the fence, rather than guessed at
a function's name standing as an argumenta call is not an argument: bind it, then pass the name
binding a -> receipt call, or a value call in statement positiona receipt binds nothing that can be consumed; a value's answer has nowhere to go — each refusal names the other spelling
a verdict name passed to a text parameterthe kinds do not convert silently; the refusal names the escape — "{v}", a hole, where the splice is visible
import in a program handed to the MCP serverthat surface takes one self-contained program and has no files to resolve a module against: inline the library, or run it with agent-cat

NineThe three commands

agent-cat plan program.wf prints the checked term — every question, its addressee, its rung, and where each answer is spliced. agent-cat cost program.wf prices it; for the flagship it prints, verbatim:

level: branch   consultations written in the term: 19   nodes: 36
shape sequence: NOT fixed by the term (`Cost.shapes` is `none` at a `case`) — this program
branches, and the cost tree below is what stands in its place.
cost tree: 9 leaves, cheapest 5, dearest 15 consultations (tick: one unit per consultation)
leaf bills, with multiplicity: {5, 6, 7, 9, 10, 11, 13, 14, 15}

…followed by the honest paragraph: the leaves are what the tree admits, a path is not a world, and the cheapest bound may be unattained. agent-cat run program.wf runs it against a real agent over ACP, with the permission and fingerprint discipline described in doc/mcp.md and the run report at the end. All three resolve import name to name.wf beside the program, and all three are one front end: an ill-typed program is refused byte-identically, with exit code 2, by all three.

TenWhat is guaranteed, and what is not

Every program this language accepts elaborates into the library's representation at or below the branch rung — Dsl.parseAndCheck_level_le, a theorem — so every program has a finite cost tree before it runs. The language has no syntax for the dynamic rung at all: data-dependent workflow shape, unbounded loops, data-width fan-out, and arbitrary code are each unwritable, which is why the bill enumeration exists. Sharing is the meaning: one binding is one answer in every world, and deliberate resampling is a different question by construction.

What is not guaranteed: that a leaf of the cost tree is attained (the cheapest may not be the bill of any run); that a receipt's act succeeded (a receipt carries no information); that the words of a prompt make an addressee produce the kind's decodable answer (the kind is the contract; {verdictSpec}-style defines are a courtesy beside it, and they can drift). The design record — including twelve things surveyed frameworks do that this language deliberately refuses, and the honest regressions of the redesign — is in doc/research/dsl-redesign/.
